# /v-method — a command whose deliverable is the method, not the plan

`/v-method <task>` takes one heavy task whose approach is unknown and writes a **campaign file**: an
ordered list of stages, each naming the command that runs it, the seats it spawns, the tools that
prove it, the evidence that lets it exit, and the observation that kills it. It writes no code and
plans no feature. `/v-team` then runs each stage.

## Read this before the design

Three limits bound every recommendation below, and none of them can be engineered away.

**No study measures whether writing a methodology up front improves the outcome.** The premise of
this command is unevidenced. What is evidenced is each component it prescribes: a verifier, a
checklist, a named constraint, a kill criterion. The command is therefore a composer of measured
parts, and it must not claim a benefit for the composition.

**No validated instrument turns a task description into a process.** Every candidate — Cynefin, the
Stacey matrix, task-technology fit — is doctrine. The routing table below is a heuristic, and every
routing decision is recorded with the task property that triggered it so later sessions can score
it against what actually happened.

**A fixed budget and guaranteed criteria cannot both be promised.** Shape Up fixes the time and
varies the scope; a goal-question-metric tree with a checklist gate fixes the criteria and varies
the time. `/v-method` asks which one is fixed in its opening exchange and states in the campaign
file what it gave up.

## Refusals

| condition | behaviour |
|-----------|-----------|
| No written problem statement naming who the output is for | stop and ask; producing a method for an unstated problem is the failure this refusal prevents |
| No success criterion expressible as `WHEN <trigger> THE SYSTEM SHALL <observable>` | stop and ask; a campaign with no observable target closes against whatever it produced |
| The task fits one session on the `/v-ask` → `/v-do` → `/v-work` → `/v-team` ladder | say which rung and stop; a campaign costs more than the work |

## Routing — checkable task property to method

One property selects one method. A task matching several gets several stages, in this order.

| task property (checkable) | method | its artifact | its stopping rule |
|---|---|---|---|
| The problem statement is not written | elicitation, then `/v-pm` | `requirements.md` naming who the output is for | a written statement exists |
| One assumption could invalidate everything | riskiest-assumption test, then a throwaway spike | a probe answering one question | the assumption is confirmed or refuted; the probe is discarded |
| The cause is unknown and the symptom reproduces | Kepner-Tregoe problem analysis | an IS / IS-NOT specification table | one candidate cause explains every IS and contradicts no critical IS-NOT |
| An automatic verifier exists — tests, types, a query | a fixed localise → repair → validate pipeline | a patch and a passing validation run | validation passes, or the attempt budget is spent |
| Information exceeds one context window | orchestrator with parallel readers | per-reader findings of 1,000-2,000 tokens each | every input item carries an identifier in some reader's output |
| One artifact, conflicting implicit decisions | a single writer with clean-context reviewers | one linear diff plus review findings | no new blocking finding, or the round cap |
| Steps depend on each other over a long horizon | plan-then-execute with a named replan trigger | a plan with named steps | every step done, or the replan trigger fires |
| A wrong direction is expensive to reverse | `/v-team` | the settled plan plus the dissent record | no new blocking finding, or the round cap with open blockers escalated |
| The criteria must be demonstrably met | a goal-question-metric tree, plus a checklist generated from the task statement and gated on | the tree, and one checklist per stage | every checklist item passes, each read from a named field |
| The budget is fixed and the scope is not | an appetite in sessions and tokens | a shaped pitch carrying the appetite | the appetite is spent; no extension without a fresh decision |
| Continuing wrongly is expensive | stage gates with teeth | per-stage kill criteria written before the stage | a kill criterion is observed, or the stage's exit evidence exists |
| The difficulty sits in one step | name the constraint and cap spend elsewhere | the named constraint and the cap | the constraint moves, then re-identify |
| Choosing between prompts, models or topologies | a factorial run table | factors, levels and the table | the factorial completes and an effect is estimable |

**Rejected routers.** A Cynefin or Stacey two-by-two classifier is not used: no classifier has been
validated, and the Stacey matrix's own author repudiated its agile adaptation. An OODA framing is
not used: it yields nothing checkable. A competing-hypotheses matrix is not a gate: the controlled
evidence against analysts is mixed to null, and trained analysts skipped its steps.

## Seats per stage

Role labels do jurisdiction work, not competence work: a seat earns its place only when it owns an
affordance or a context slice the single agent cannot have. The default three seats are analyst,
implementer and tester, and the analyst seat carries most of the measured gain.

| stage | seats | the affordance each owns |
|---|---|---|
| understand | `requirements-analyst`, `personas/_shared/consumer.md` | the analyst writes the specification; consumer produces one real output from the text the receiver gets |
| plan | the pack architect, the one lens the task's keywords trigger, `personas/_shared/skeptic.md` on high stakes, `personas/_shared/proof-auditor.md` | each holds a different analyzer; the auditor re-runs the grounds the drafter asserted |
| execute | one writer, spawned as the architect's `base_agent` | it holds the diff; a second writer resolves the same implicit decision differently |
| verify | `personas/_shared/correctness.md`, the group at `personas/_shared/testing/`, `personas/_shared/proof-auditor.md` | tests, analyzers and fetch — evidence the writer did not hold |

**Panel size.** Three seats by default, five as the hard ceiling, sized by a pilot at five or fewer
before any larger fan-out. A dense panel past that point degrades: added members share evidence
sources, and aggregation amplifies a shared error instead of cancelling it.

**Cost.** A subagent fan-out costs roughly four times a single-agent run in tokens, and a
many-seat panel roughly fifteen. At an equalised thinking budget a single agent matches or beats a
multi-agent team on multi-hop work, so the fan-out buys context isolation and tool asymmetry, never
headcount.

## Tools that prove a stage independently

Ordered by leverage per hour of setup. Each catches a defect class no reading reviewer catches.

| tool | defect it uniquely catches | cost |
|---|---|---|
| `diff-cover --fail-under` | a changed line no test executes | the cheapest hard gate available |
| `osv-scanner`, `npm audit`, `pip-audit` | a new dependency carrying a published advisory | zero setup |
| `tsc --noEmit`, `mypy`, `phpstan` | every call site inconsistent with a changed signature, repo-wide | free on a typed repo |
| `go test -race`, ASan, TSan, UBSan | a data race or memory error on tests that already pass | one compile flag |
| `mutmut`, `stryker`, PIT, scoped to the diff | a test that executes a line and asserts nothing | diff-scoped only; whole-repo runs do not finish |
| OpenTelemetry in-memory span assertions | an N+1 query, a retry that never fires, a cache that never hits | needs instrumentation; the highest-leverage untapped check |
| a two-run metamorphic assertion | a wrong result where nobody knows the right answer | an ordinary test; inventing the relation is the work |
| `hypothesis`, `fast-check` | boundary and degenerate inputs nobody enumerated | authoring the invariant is the cost |
| `semgrep --config auto --error` | mechanical defect patterns | capped at one wrong finding in ten, per `vault/check-budget.md` |
| `rr replay`, `vcrpy`, a Playwright trace | a failure that does not reproduce | Linux and x86 only |

**Diff-scoped mutation carries a known ceiling:** across 357 real faults in five Java programs,
73% coupled to at least one mutant and 27% to none. It measures whether a test would catch a
defect, not whether the code is right.

## Tools that prove a claim independently

These arm the auditor seat. Each is one command and each has a stated limit.

| signal | command | what it does not prove |
|---|---|---|
| the cited work exists and is not retracted | `curl -s 'https://api.openalex.org/works/doi:<DOI>?select=title,is_retracted'` | that it says what was claimed |
| the maintainer deprecated it | `curl -s https://registry.npmjs.org/<pkg>/latest \| jq -r .deprecated` | that the named replacement is right |
| the runtime is past end of life | `curl -s https://endoflife.date/api/<product>.json` | vendor extended support |
| the standard is superseded | `curl -s https://www.rfc-editor.org/rfc/rfc<N>.json \| jq .obsoleted_by` | W3C, ECMA and ISO have no equivalent field |
| an advisory is open | `curl -s -X POST -d '{"package":{"name":"<p>","ecosystem":"npm"}}' https://api.osv.dev/v1/query` | reachability; no advisory is not safety |
| what the page said when it was cited | `curl -s 'https://web.archive.org/cdx/search/cdx?url=<u>&output=json&filter=statuscode:200'` | uncrawled and JavaScript-rendered pages |
| the claimed wording is on the page | `curl -sL <url> \| strip-tags \| grep -i -C2 "<phrase>"` | meaning, context, inversion; a miss proves nothing |
| the sentence is entailed by its source | `minicheck` run locally | anything outside the document supplied to it; the model is multiple gigabytes |
| every part of a multi-part claim was searched | decompose the claim, then one search per part | an unsearchable claim, and contaminated results |

**Four signals ship nothing.** Source independence for blogs and documentation has no tool — the
published algorithms need a whole citation graph, not five URLs. AI-generated-source scoring ships
nothing: all fourteen detectors tested scored under 80%, so a false positive rejects a correct human
source. The ThoughtWorks Radar has no machine-readable dataset. Google's Fact Check API refuses
unregistered callers. The Wayback availability endpoint returns 429 under repeated use; the CDX
endpoint above is the one that answers.

**Adoption volume is not currency.** The deprecated `request` package draws over fifty million
downloads a month and last released in February 2020. A standing signal is advisory evidence a
reviewer interprets, never an automatic rejection.

**No per-result spam score exists, so require one primary artifact per claim instead.** The rule
that replaces the missing detector: a claim about a library, a standard or an approach cites the
maintainer's own changelog, release notes, RFC record or archived statement. A third-party article
corroborates; it never carries the claim alone.

**A citation count names the API that produced it.** Crossref, OpenAlex and Semantic Scholar
returned 465, 602 and 676 citations for one paper on one day.

## The seam with /v-pm

Two commands, two questions, and they do not overlap.

| question | command | its output |
|---|---|---|
| What must the product do | `/v-pm` | `requirements.md` rules `REQ-NN`, the glossary, the variant and state tables, and an appetite per repo |
| How do I work on it | `/v-method` | `method.md` — the stages, their seats, their tools, their kill criteria |
| What exactly changes in this repo | `/v-team` | the plan, and the `## Sessions` rows inside one stage |

Order depends on what is unknown. A task whose business logic is unclear runs `/v-pm` first, because
the method cannot be chosen for an unstated problem. A task whose requirements are clear and whose
approach is not runs `/v-method` first.

`/v-method` writes `method.md` beside `generic-plan.md` in the same `_features/<feature>/` workspace
when one exists, and into `<project-vault>/plans/` when it does not. It consumes the appetite
`/v-pm` wrote and never re-derives it. Its stage rows are coarser than session rows: it orders and
sizes the stages, and `/v-team`'s own decomposition still splits the work inside one stage. A
campaign whose stages do not fit the appetite cuts scope and records the cut rather than exceeding
the budget quietly.

## Why a gate between stages holds, or does not

A stage gate holds on two conditions, both required. The kill criteria are written **before** the
stage runs, and the reader of the gate has the authority to stop the work. A gate whose criteria are
written after the evidence arrives is a rubber stamp.

The failure to design against is a gate reading the wrong field. One production gate flagged none of
a hundred cases it should have caught because its condition read a field that was always empty. So
every kill criterion in a campaign file names the exact file and field its verdict is read from, and
the campaign's own check script re-reads that field rather than trusting the stage's report.

`bin/gate.sh verdict --run` is the mechanism that makes this real: it executes the named script and
writes the verdict and the captured output into the file itself. No model grades a stage.

A checklist generated from the task statement is what turns "the criteria were met" into something
a gate can read. Checklist feedback beat a trained reward model on every benchmark it was tested
against, so the checklist is written at planning time and the gate runs against that exact list —
never against a list assembled once the evidence is in.

A loop names its signal, its interval and its iteration count, or it is a single pass wearing a
loop's name. Fewer than one in five published improvement-cycle projects documented more than one
cycle, at 14 of 73.

## What this brief does not settle

| item | state |
|------|-------|
| Whether a campaign file measurably beats starting the work and adapting | open — unmeasured; the command records its routing so this repo's own runs become the evidence |
| Whether `/v-method` is a command or a mode of `/v-pm` | answered — its own command; a feature's requirements and a task's method are two questions, and one file answers one question |
| The campaign file's exact schema and its check scripts | open — designed in the session that builds this |
| Whether the routing table's properties can be decided mechanically from a task statement | open — each row claims a checkable property, and none has a function behind it yet |
