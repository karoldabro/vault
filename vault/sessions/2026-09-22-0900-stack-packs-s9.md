# stack-packs-s9

## Goal
Land S9 of the architecture-first-planning master plan: probe-registry stack packs for Laravel, Nuxt,
Flutter and Python, gated by a repo-declared `stack_packs` VAULT.md key.

## Did
- Added five `probes/registry.tsv` rows and their `lib/probe-parsers.sh` parsers: PHPStan +
  PHPArkitect (Laravel), ruff (Python), `dart analyze` (Flutter), vue-tsc (Nuxt).
- Added a `stack_packs` key to `templates/VAULT.md`, detected at onboarding by
  `bin/vault-init.sh` and read by a new `probe_vault_key` helper + row filter in `bin/probe.sh`.
- Documented the key in `commands/_shared/probe-kit.md`, added six unit tests (T-40–T-45) to
  `tests/unit/probe.bats`, all against real captured tool output in `tests/fixtures/probe/`.
- Wrote and ran seven check scripts (`checks/stack-packs-SC-1.sh` to `SC-7.sh`) — all seven MET.
- Added `recycling-api/probes/registry.tsv` (uncommitted, in that repo): a repo-scoped
  `laravel-phpstan-docker` row that runs PHPStan inside that repo's own `server` Docker image, since
  its `vendor/` needs PHP >=8.4.1 and this machine only has 8.3.

## Learned
- `flutter analyze` (3.44.4) has no `--format` flag at all; `dart analyze --format=machine` (the
  bundled Dart SDK command) is the real machine-readable path.
- `vue-tsc`/`tsc`'s piped (non-TTY) diagnostic line is the parenthesized non-pretty form,
  `path(line,col): error TSxxxx: msg` — the colon-dash pretty form is TTY-only.
- PHPStan's `--error-format=json` has no severity field on a message, only `ignorable`; PHPArkitect's
  JSON is keyed by fully-qualified class name with no file field at all.
- `bin/vault-init.sh` runs under `set -euo pipefail`; a `{ find ...; ls missing-file; } | grep -q .`
  detect pattern that works fine as a `probes/registry.tsv` `detect` cell (run via a fresh `bash -c`,
  no pipefail) silently breaks under `pipefail` — `ls` failing on a missing file poisons the whole
  pipeline's exit status even when `grep` found a real match. Every command in such a group needs its
  own `|| true` when the caller has `pipefail` on.
- `sed 's#/app/##'` (no `g`) only strips the first match per line; PHPStan's JSON is one line, so every
  `/app/` after the first survived, producing absolute paths that `probe_finding` refuses as malformed.
- A full-project PHPStan scan of `recycling-api` took over 10 minutes and still errored out; scoped to
  `app/Http/Controllers` it runs in under two.
- `vault/research/probe-tool-verification.md` already committed session S9 to PHPArkitect and named
  PMD CPD as a pending addition — a plain grep over `vault/indications/features/processes/architecture`
  during LOAD CONTEXT misses `vault/research/`, which needs its own check when a plan adds a new tool.

## Behaviors & rules
- `probes/registry.tsv` row whose `stack` is not `any`/`harness` and is not listed in the repo's
  `VAULT.md` `stack_packs` → `bin/probe.sh` skips it silently, no `ran:`/`absent:` line; edge: an
  empty `stack_packs:` value behaves as if the key were absent, never as "zero stacks".
- `bin/vault-init.sh` onboarding a repo with `composer.json` naming `laravel/framework` and a `.sql`
  file under `database`/`migrations`/`db`/`schema` → writes `stack_packs: laravel, sql` to that
  repo's `VAULT.md`.
- `commands/_shared/probe-kit.md` §"Adding a probe" step 1 (record a tool in
  `vault/research/probe-tool-verification.md` before adding its registry row) is binding on every new
  probe, not just SQL/harness ones — enforced here by a lite critic's review, not by any gate.
